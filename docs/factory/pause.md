# Pause

The circuit breaker for one target: the repository variable `FACTORY_PAUSED`, read by the caller's job conditions. Empty or unset means running, any other value pauses, and the value is the reason. README has the two commands.

- **What stops.** `dispatch`, and the reconciler with it, `implement`, `review`, `implement-pr`, `update-branch`. Everything that starts work or moves it along. Since #256 the heartbeat stops too: it reads the variable before waking a target and skips a paused one, so the sweep that drove all of the above is not sent in the first place.
- **What does not.** `merge-gate` and `audit`, both asked for by a pull request that already exists rather than by the factory's own initiative. `merge-gate` runs no agent at all. `audit` does run one, and on a miss it pushes a revert branch, opens a revert PR and opens a `needs-human` issue, so "keeps running" means exactly that and not "does nothing". It stays anyway: it is bounded, one run per merged PR inside the first-20 window, it never starts a ticket or puts an agent on a branch, and a bad merge that landed just before the pause is the thing you most want caught while everything else is stopped. Its revert PR is the alarm, not new work.
- **Why the line falls there.** A pause never takes the factory's checks off a PR. That is the whole of #171: before it the only breaker was `gh workflow disable factory.yml`, and because that one file is the caller for every role it dropped `factory/red-green` and `factory/test-integrity` from every PR opened while it was off. The checks did not fail, they never appeared, which is worse than a red check because nothing says so.
- **A pause is not a hold.** `hold` (#186) holds one ticket back and lives on that ticket; a pause stops the whole target and lives on the repo. Reaching for `hold` during an incident is the slow version of the wrong thing: it takes one write per ticket, and the runs in flight carry on: since #185 it stops the retries and repairs the factory would decide on after them on that ticket, but it interrupts nothing already running, and a run that succeeds still hands its PR to the reviewer.
- **What a pause does not do.** It does not cancel a run already in flight: a job that started before the variable went on runs to its end, and the pause only stops the next one. It does not make a PR mergeable either, and on a paused target rather less is mergeable than usual: `factory/verdict` is required and only the gated `review` job posts it, and the ruleset is strict, so a PR that falls behind main waits for the gated `update-branch`. Repository admins still bypass, as they always did. A pause protects a PR's checks, it does not land the PR.
- **A pause is what makes a cancel stick.** `gh run cancel` on its own does not stop a ticket: the retry handler reads a cancel as the implementer's own failure (#51) and re-adds `agent:implement` within a minute or two, and at the stuck deadline the reconciler would too. Both of those are label writes, and the caller's `implement` job is gated, so with the pause on they land on the ticket and start nothing. So the order in an incident is pause first, cancel second. Cancelling first just races the handler.
- **Why a variable.** `vars` is readable in a job-level `if:` and `secrets` is not. A variable is also in the repo's settings UI with its value in plain sight, which is where the reason lives, and `gh variable set` is one command that needs no knowledge of what is in this file. `FACTORY_PAT` cannot write repo variables (see [onboarding.md](onboarding.md)), so the factory can neither pause nor resume itself.
- **Why a skipped job and not a disabled workflow.** Anything that defers or queues events starts a backlog the moment it is lifted, and a disabled workflow is the same failure from the other side: it drops events on the floor with no record. A gated job's `if:` evaluates to false and the job is skipped before a runner is assigned, so the event is spent rather than held, and the skip bills no runner time.
- **What a resume actually starts.** Nothing retroactive. The factory picks up from the repo's state on the next heartbeat, the same state any sweep reads: tickets still `ready-for-agent` are dispatched then, and a subject left mid-run when the pause landed is repaired by the reconciler at its deadline. So a resume starts what a sweep would start now. Label ten tickets during a pause and the first sweep after it dispatches ten, because ten tickets are ready, not because ten events were held. **So fix the cause before resuming.** The queue is empty, but the repo's state is not, and a resume with the runaway's cause still in place restarts the runaway from that state. Nothing in the mechanism can tell those two apart, which is why it is written here as an instruction rather than promised as a property.
- **A pause cannot let anything merge unjudged.** `factory/verdict` is required and a paused reviewer never posts it, so ADR 0003's gate tightens under a pause rather than loosening. It tightens twice over, because gating `update-branch` gates a merge path too: arming auto-merge enrols a PR in `update-branch` (ADR 0006) precisely because the ruleset is strict, so a PR that falls behind main while paused stays behind it and waits for the resume. The one thing a pause does not hold is a PR already green and already up to date with main, which auto-merge lands as soon as the last check goes green: auto-merge is GitHub's, armed before the pause.
- **What a pause costs.** Nothing on an interval, since #256. The gate is a condition on each job and not a filter on the trigger, so before that the heartbeat woke a paused target every interval, GitHub created a run, the `paused` job ran to say why everything was stopped, and every work job was skipped: the pause stopped the work and not the run. Measured on one private target on 2026-09-12, each such run reported about three seconds of billable job time, which GitHub rounds up to the minute, and five runs landed in a forty minute pause: six minutes an hour, about 144 a day, to be told repeatedly that nothing was happening. The heartbeat now reads the pause before the wake and skips a paused target, so no event is sent and no run exists. What is left is the events the target raises itself, a label going on or a push, each still answered by a run whose only job is `paused`: the cost is one runner minute per such event, and for an event that would wake a job unpaused that is what the event already cost.
- **Visible while it is on.** The variable, plus a `paused` job in every factory run for as long as it is set: a `::warning::` annotation and a step summary naming the reason and what is still running. It is the caller's only job that calls no reusable workflow, and it earns its place because a skipped job is still an absence, which is the inference #171 refuses. The heartbeat is the second place it shows, and for the same reason: a paused target is reported every pass as skipped for the pause, with the reason, and not as one skipped for having nothing waiting. Two skips that read alike is how a pause left on is mistaken for a quiet week.
- **What the heartbeat's skip does not touch.** `merge-gate` and `audit`, the two the pause deliberately keeps. Neither is driven by the heartbeat: both fire on pull request events raised by the target itself, so removing the wake removes the sweep and leaves those two exactly as they were. `dispatch/triggers.test.ts` pins it, because a later change that hung either off `factory-sweep` would make a pause drop a human's checks by a different door than the one #171 closed.
- **The crude lever, if a target's heartbeat is not this one.** Parking every open ticket and pull request with a label the heartbeat treats as parked stops the wake too, and it is what was used before #256: six consecutive skipped passes, zero minutes. It costs a label on every subject by hand and the same again to undo, so it is a fallback and not the mechanism.
- **A pause the heartbeat cannot read is a failed target, not a running one.** The read is a GET of the variable, and unset is a 404, which means running; any other failure fails that target for the pass and exits the sender non-zero, the same as an unreadable open-work read. Reading a failure as "not paused" would wake a paused target every interval behind a read nobody noticed was broken, which is the cost this is here to stop. A 404 is asked a second question for the same reason: a fine-grained token holding the repo but not Actions variables read is answered 404 on a variable, exactly as GitHub answers one that is not set, so a token missing that scope would hand back "not paused" for every target it covers. The list endpoint tells them apart, since a token that may read answers it 200 with a count of zero on a target that has no variables, and a 404 there is the permission rather than the variable. A target really paused never reaches the second question: its value already answered it. **So a target whose token predates the scope fails loudly rather than being woken in silence**, which is the one way a maintainer finds out.
- **It lives in the caller, so it drifts silently**, the same way the trigger set does. A target that has not re-copied `templates/factory.yml` since #171 has no gate at all and `FACTORY_PAUSED` set there does nothing; nothing in the factory can see a target's copy. Until the re-copy, `gh workflow disable` is still that target's only breaker, with the cost above.
