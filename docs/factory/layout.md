# Layout

- `.github/workflows/`: an `agent-` prefix means the workflow runs a model, sandcastle's convention. `agent-implement.yml`, `agent-review.yml` and `agent-implement-pr.yml` are the reusable workflows, one per vendored sandcastle workflow, under his names, each ending in the `retry` job the retry-and-escalation topic describes. `agent-audit.yml` is the first-20 audit, factory-owned, with no sandcastle counterpart. The rest run no model and are all factory-owned: `merge-gate.yml`, `dispatch.yml`, `update-branch.yml`, and `ci.yml`, this repo's own CI.
- `factory/agent-workflows/`: the vendored sandcastle 0.12.0 scripts and prompts, under his own folder name and laid out as his `.sandcastle/agent-workflows/` (`implement/`, `review/`, `implement-pr/`, `shared/`). One path, one rule: under `factory/`, this folder is his and everything else is ours. It is a provenance boundary, not a dependency one: his `run-with-extraction.ts` is called from `factory/lib/run-agent-workflow.ts`, and the primitives our modules once took from his `shared/common.ts` now live in `factory/lib/` with the rest of ours (#313). His section headings stay his so an upstream diff stays readable, so a vendored prompt heads its ticket section `# ISSUE` while a factory-authored one uses `# TICKET`. `docs/provenance/sandcastle-files.md` maps every file to its origin and holds the rules for changing one; `CONTEXT.md` records the heading exception.
- `factory/lib/`: the factory-authored modules the workflows run on, the ones that are not a workflow of their own (`gh.ts`, `target-repo.ts`, `labels.ts`, `factory-pr.ts`, `model.ts`, `run-log.ts`, `harness.ts`, `ticket-context.ts`, `plugins.ts`, `pr-disposition.ts`, `usage.ts`, `usage-record.ts`, `read-only.ts`, `rotation.ts`, `accounts.ts`, `claude-agent.ts`, `run-agent-workflow.ts`, `trusted-authors.ts`, `linked-issue.ts`, `verdict.ts`, `errors.ts`, `conflicts.ts`, `preflight.ts`, `env.ts`, `sh.ts`, `run-output.ts`, `coerce.ts`, `upsert-comment.sh`), plus `repo-files.ts`, which only the tests use. `run-agent-workflow.ts` is the shell every agent workflow runs inside, and `claude-agent.ts`, `env.ts`, `sh.ts`, `run-output.ts` and `coerce.ts` are where #313 rehomed the helpers his `shared/common.ts` used to hold in one bag. `target-repo.ts` is the shared module named after CONTEXT.md's **Target repo**: it holds the GitHub-backed reads and writes the scripts make against one, written once and choosing the reading or writing key per function.
- `factory/merge-gate/`, `factory/dispatch/`, `factory/update-branch/`, `factory/retry/`, `factory/audit/`: one folder per factory-owned job, `retry/` being the `retry` job of the two implement workflows rather than a workflow of its own. Each keeps its workflow's decisions as pure, `node --test` covered functions, and the script beside them only gathers inputs and calls GitHub: `dispatch/select.ts` and `dispatch/reconcile.ts`, `update-branch/plan.ts`, `retry/decide.ts` and `retry/escalation.ts`, `audit/plan.ts`, and the modules under `merge-gate/` that `merge-gate.ts` runs. The dispatch, update-branch and audit-decide jobs install nothing and run on Node's type stripping, so a sweep costs seconds, billed as a minute on private repos.

## How a script is wired

The heartbeat is the pattern (#222, #281): a script declares what it needs from a target as a **needs record**, a record of named domain reads and writes in the shape of `heartbeat.ts`'s `Pass`, and is handed them from outside so it can be rehearsed against a pretend repo. `heartbeat.ts` decides and `send.ts` wires it; the sweep now splits the same way.

- `dispatch/sweep.ts` is the sweep: it takes a `Needs` record, builds the reconciler's snapshot from it, decides with `reconcile.ts`, and applies the repairs. No `gh` call lives in it, and a test drives it with an in-memory target repo (`dispatch/sweep.test.ts`).
- `dispatch/sweep-run.ts` is its entry point, what `dispatch.yml` runs: it reads the env, assembles the record from `lib/target-repo.ts`, runs the pass and sets the exit code.
- `dispatch/dispatch.ts` splits the same way (#286): it takes a `DispatchNeeds` record, reads open issues through the shared projection rather than a full payload, asks `select.ts` what to dispatch, and writes the label and the one no-criteria comment; `dispatch/dispatch-run.ts` is its entry point and `dispatch.test.ts` rehearses it. `target-repo.ts`'s `dispatchNeeds` backs it. What it selects did not change.
- `update-branch/update-branch.ts` is wired the same way (#287): it takes its own needs-record, plans with `plan.ts`, and applies the update, statuses, comments and labels; no `gh` call and no status-key env live in it. `update-branch-run.ts` is its entry, and `update-branch.test.ts` drives it against an in-memory target repo. `target-repo.ts`'s `updateBranchTargetRepo` picks the key: commit statuses use the reading key (`READ_TOKEN`), everything else the writing key.
- The key choice lives in `target-repo.ts`, not the script, and the two keys have two settled names: the writing key is `FACTORY_PAT`, the reading key (the reads a fine-grained PAT cannot make: Actions runs and jobs, commit statuses) is `READ_TOKEN`. The old names each replaced (`GH_TOKEN` for writes, `STATUS_TOKEN` and `GH_TOKEN` for reads) were dropped by the contract ticket (#288), so a script wired with only an old name is refused with a clear error naming the key it is missing. The rollout was expand, migrate, contract (#282, #283, #288) because targets pin `@main`: the factory accepted both names, every target's caller switched, then the old names went.
- Which reads may fail softly stays the script's own policy: `target-repo.ts` always throws `GhError`, and the sweep catches the four it shrugs off (a ticket's author, a run's jobs, a PR's comments, its own login) and leaves the subject alone; the dispatcher shrugs off only the no-criteria comment's read, a courtesy.
- `retry/retry.ts` is the retry handler's failed-attempt path (#284): given a resolved target and a built failure, it decides with `decide.ts` and writes through its own `RetryNeeds` record, with no `gh` call, and a test drives it against an in-memory target repo (`retry/retry.test.ts`). `retry/retry-run.ts` is its entry point: it reads the env, assembles the record from `target-repo.ts` (`retryTargetRepo`), builds the failure and calls `main`. The soft-fail policy stays the handler's, in its `soft`.
- The retry handler's wait for a head's checks is `retry/retry.ts`'s `waitForChecks` (#285): the poll loop and its decision (`waitOver`, `stillPendingReason`), reading through a `ChecksNeeds` record that carries a `now` and a `sleep` the way the heartbeat's `Pass` carries `now`. `retry-run.ts` assembles the real record (the head's checks, a PR's mergeability, the failing output, and the wall clock and `setTimeout`); `retry/checks-wait.test.ts` drives each outcome by advancing an injected clock, so the wait is rehearsed with no real time passing. The log and artifact reads that build a failure's output stay in `retry-run.ts`.
- `factory/guards/` and `factory/onboard/`: tests for things that live outside `factory/`, the harness guards under `scripts/guards/` and `scripts/onboard.sh`, here because `npm test` globs `factory/**/*.test.ts`.
- `factory/plugins/`: skills the prompts call by name, vendored whole and pinned (mattpocock-skills 1.2.3, all 25 skills its manifest declares, including `tdd`, `code-review` and `resolving-merge-conflicts`). Copied into the account's `CLAUDE_CONFIG_DIR/skills/` before each attempt, where Claude Code loads them as plugins. The marketplace installer takes no version, so vendoring is the pin, and `factory/plugins/README.md` says how to bump it.
- `scripts/`: `onboard.sh`, and `guards/` for the checks that refuse a tool call in a maintainer's own harness, wired from `.claude/settings.json`.
- `templates/`: `factory.yml`, the caller a target copies into its `.github/workflows/`, `routing-test-command.sh`, the worked routing test command a target with two kinds of test copies beside it, and `agents-md-judged-path.md`, the one line every target puts in its `AGENTS.md` so a session opening a PR itself takes the judged path (#181). sandcastle's word for the folder.
- `.github/dependabot.yml`: opens a PR when a new sandcastle or Claude Code version ships. The pin only moves by hand.
- `docs/`: `pipeline.md` the router, `factory/` one file per topic behind it, `adr/` the decisions, `agents/` the rules binding an agent working in this repo, `provenance/sandcastle.md` why the engine is vendored rather than forked plus what was not copied and why and spec #9's stories on sandcastle, `provenance/sandcastle-files.md` every file mapped to its origin plus the rule that changing a vendored file updates that row's counts, `research/` dated snapshots an ADR cites, never updated.
