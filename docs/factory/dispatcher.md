# Dispatcher

Runs on the caller's issue events (the trigger set is pinned in `docs/pipeline.md`), on `workflow_dispatch`, and on the `repository_dispatch` event `factory-sweep`. The caller has no `schedule` trigger: GitHub's cron was removed in #270, and the heartbeat sending `factory-sweep` is what drives the sweep on an interval (the router states the run command and cadence).

A `labeled` run is for `ready-for-agent` and nothing else. An `unassigned` run is admitted whoever dropped the assignee, and an `unlabeled` run for any label outside the factory's own two namespaces, `agent:*` and `factory:*`, so that a ticket stopped by `hold`, by `needs-human` or by an assignee reaches the factory the moment the human lets go of it instead of waiting for the next heartbeat. Every one of those is admitted on an open ticket only (#213 for the two removals, #236 for the two labels going on): `select.ts` refuses a closed ticket whatever it carries. A `closed` run is still admitted, because closing one ticket can unblock another. So the caller states one rule: the factory acts on open tickets, and the only thing worth hearing from a closed one is the close itself. Which of the admitted removals can actually unblock a ticket is `select.ts`'s answer, and the rules below are its only copy: a caller that named them would be a second copy drifting quietly out of step, so a run over a ticket nothing unblocked labels nothing. The caller's condition says which action each of its clauses is for, because an `unassigned` payload carries no label and a clause reading `github.event.label.name` off one would compare against null and drop the event with no error anywhere.

## Why the caller drops its own namespaces

The two namespace clauses are not part of that rule, they are a loop breaker (#170). Every label the factory writes goes in with `FACTORY_PAT` so the write fires its event, which is what lets adding `agent:implement` start an implementer, and that cuts both ways: the factory's own label *removals* woke a full sweep too. A run's cleanup step takes its `agent:*` label off, the sweep that removal woke found the ticket takeable in the gap before the next label went on, and re-stamped `agent:implement`. Cancelling a run therefore bought a replacement within seconds. Observed on one target: twelve runs cancelled one after another and the in-flight count went up, from twelve to fourteen, with twelve fresh runs inside two minutes, and only `gh workflow disable` stopped it.

What that leaves. The sweep no longer replaces a cancelled run, so the amplifying half is gone: a cancel can no longer produce more runs than it stopped. Two bounded paths still bring a cancelled ticket back, both at most once per cancel:

- The retry handler. A cancelled `implement` job still reaches the `retry` job, because that job is gated on `always()` and a cancel is deliberately read as the implementer's own failure (#51: a `timeout-minutes` kill and a human cancel are the same outcome at that seam, and a kill is exactly what a retry is for). It spends the ticket's one retry and re-adds `agent:implement` within a minute or two, with no sweep involved. A second cancel finds the retry spent and escalates to `needs-human`.
- The reconciler. A ticket left in a factory state label with no live run is repaired at `stuck_minutes` (default 30) on the next heartbeat. It counts the cancel as a lost event and therefore a miss, and two misses escalate to `needs-human`.

So a cancel now buys one delayed replacement rather than an outrunning stream of them, and cancelling twice parks the ticket for a human. Telling a human's cancel apart from a job timeout, so that a deliberate cancel stays cancelled outright, is #185: it lives in the retry handler, not in the caller, and nothing here can reach it.

One factory write still wakes a sweep, deliberately: escalation takes `ready-for-agent` off, and that is outside both namespaces. It is one sweep and it labels nothing, because the label whose removal woke it is the one `select.ts` checks first. By the time that sweep reads the ticket, `ready-for-agent` is already off it, so the answer is `no ready-for-agent` and nothing is written. That does not depend on the rest of the escalation having landed, which is the point: the between-writes gap is exactly what caused #170, and this exception does not sit in one. (`needs-human` going on refuses the ticket too, but it is the second reason, not the one being relied on.) A rule phrased over the event's *sender* would have covered that write as well, at the price of every caller naming the factory's GitHub account: new onboarding surface, and an account identity published in every target's workflow file, which this repo deliberately keeps out of what a target carries. The namespace rule needs no configuration at all and is readable from the caller alone, so it wins and the one uncovered write is named here instead of papered over.

What a human loses: taking an `agent:*` label off a ticket by hand no longer reaches the factory at once, it waits for the next heartbeat. That was never the documented hand-back, which is `needs-human` off and `ready-for-agent` back on, and both of those still reach the dispatcher immediately.

## Heartbeat

**The heartbeat is what drives the sweep, and it is the only thing that does.** Measured on `chizhangucb/tomte-fixture` over 21 and a half hours from 2026-09-08T21:07Z: GitHub's own cron fired 6 times against about 129 expected at six an hour, while the heartbeat sending `factory-sweep` fired on every interval in the same window, so the cron was removed from the caller in #270. The sender runs `factory/heartbeat/send.ts` from an outside host (the router pins the command and how often), with a token that has contents write and issues and pull requests read, plus Actions variables read for the pause and the waiver nag, on every target in `factory/heartbeat/targets.ts` and nothing else. It keeps one file of its own, `~/.factory-heartbeat-passes` (`FACTORY_HEARTBEAT_PASS_LOG` moves it), and names it in the pass when a run of passes stops agreeing with the documented interval, since the host's schedule is the last copy of that number this repo cannot see (#265).

The sender lives here rather than on one machine (#222): each interval every target on that list is read and then woken, skipped for a pause, skipped as idle, left asleep with nothing due or reported failed, and a failure exits non-zero without costing the targets behind it their sweep. A target is woken when it is not paused (#256), something unparked is waiting on it, a ready ticket or a ticket in a factory state label that nothing holds, or any open pull request, held or not (#212), and a sweep would act on one of those now (#264). The pause is asked first, because it settles the question on its own and reading a paused target's open work would answer nothing. Without the heartbeat the dispatcher and the reconciler below run only on the target's own events, since the caller has no cron of its own (#270). Where the heartbeat runs, and the token it uses, is #111.

### The interval derivation

**Why the interval is what it is, and where the number lives** (#261, #271). A deadline is only ever checked when a sweep runs, so the interval is added to every one of them: a subject that crosses its deadline waits up to one further interval for the sweep that repairs it, landing between D and D + I for deadline D and interval I. No interval makes a deadline exact, and the only question is how late is acceptable. The interval is the tightest deadline, `stuckMinutes` in `DEFAULT_DEADLINES`, which caps the worst case at twice that deadline. **That is a judgement, not arithmetic**, and it is worth saying so, because the cheaper-sounding argument, that a larger interval stops a deadline being a deadline, is false: at 30 and 30 a stuck subject is still repaired somewhere between 30 and 60 minutes. What the interval changes is the multiple, 1.5 times the deadline at 15, twice at 30, three times at 60, against a billed minute per pass on every target with work open. Twice is where this repo has settled, and every reconciler deadline is 30 now (#271), so the tightest one the interval follows is 30. The number itself is `HEARTBEAT_INTERVAL_MINUTES` in `factory/heartbeat/interval.ts`, stated in `docs/pipeline.md` and README and nowhere else: `interval.test.ts` holds it to the rule, and `send.test.ts` holds both pages to it and refuses any other file that restates it. What the interval follows is `DEFAULT_DEADLINES` in `factory/dispatch/reconcile.ts`, which is what `interval.test.ts` reads: raising the tightest default is what lets the interval rise, and it fails that test until a human moves the constant too. A target that overrides `stuck_minutes` in its own caller moves its own deadline and not the interval, so setting one below the interval buys that target no faster repair.

### What is due, not what is open

Every repair the reconciler makes is gated on one of its deadlines (#264), and a deadline is only ever checked when a sweep runs, so the pass that matters is the first one after it falls: the sweep acts then, and the repair changes the subject, which starts the next deadline. `work.ts` wakes a target on that pass and not on the ones between, and imports `DEFAULT_DEADLINES` so no deadline has a second copy, the route `PARKED_LABELS` already travels from `factory/lib/labels.ts`. A subject is due on three counts: a deadline fell in the last interval, it changed since the last pass, or it is a ready ticket the dispatcher has not picked up, which has no deadline running at all. Its clock is `updated_at`, one field more on the read the pass already makes. Measured against the shape in #264, a subject open and untouched for two hours used to be swept on every pass; with the interval at 30 and every reconciler deadline at 30 (#271) two hours is four passes, and one subject is woken twice, on the pass that lands with its change and again on the pass after its single deadline, and on no pass after, so raising the interval is no longer the lever on what the factory costs. Two limits, both deliberate: a target that overrides `stuck_minutes`, `verdict_minutes` or `update_minutes` in its own caller is still reasoned about on the factory's defaults, because the factory cannot read a target's caller, and a deadline that fell during passes the host never ran is caught by the daily recheck (#267), which retries a repair that changed nothing rather than waiting on an edge that has passed. Waking on the defaults is the safe direction and beats waking always. One caveat on that number: it is one measurement, and it is from a private repo.

## What the dispatcher dispatches

- It dispatches an open, `ready-for-agent` ticket from a trusted author with no open blockers (GitHub native issue dependencies, `issue_dependencies_summary.blocked_by`), no assignee, no sub-issues, no `agent:*` or `needs-human` label, no open PR already closing it, and a checklist under an acceptance-criteria heading in its body (#257). A ticket carrying `hold` is held back whatever else it says; what it means to a triager is in `docs/agents/triage-labels.md`. A ticket is a sub-issue of its spec and is picked up as one; a spec is refused, whether its title starts `Spec:` or it has sub-issues of its own (#296).
- The issues listing is eventually consistent, so before each label the dispatcher re-reads that issue (state, labels, blockers, open PRs) and skips it with `closed since the snapshot` or the usual reason when anything changed; the summary line counts them. `agent-implement.yml` is the backstop, refusing a closed issue (label removed, comment) before it touches a branch. Both exist because #19 labeled and implemented two closed tickets, and merged one.
- Removing a hold releases the ticket on the next sweep, and nothing else has to be done to it. Taking the label off fires `issues: unlabeled`, which wakes the dispatcher at once on a target whose caller subscribes to it: `hold` is a human's label and sits outside the `agent:*` and `factory:*` namespaces the caller drops (#170), so its removal is one of the admitted ones. The sweep catches it anyway if that event is lost. Within one heartbeat interval on a target being sent `factory-sweep`, then, and no promise at all on one that is not: the heartbeat is the only thing that sweeps on an interval, since the caller has no cron of its own (#270), so a target nobody sends it to releases a ticket only when one of its own events wakes the dispatcher and no sooner. A caller still subscribing to `closed` and `labeled` alone does not get the `unlabeled` wake either, and waits for that sweep. Work already in flight is the exception to the wake (#185): a PR the retry handler stood down on, or a ticket held with its start label still on, is one the dispatcher will not take, and the reconciler resumes it on its first sweep past the stuck deadline.
- Labels go on with `FACTORY_PAT`. A label added with `GITHUB_TOKEN` fires no `issues: labeled` event, so the implementer would never start.
- A skipped ticket is not commented on, with one exception; the reason is one line per issue in the job log and the `dispatch.json` artifact, so a sweep on every interval does not become a comment on every interval. The exception is the ticket with no acceptance criteria (#257): every other reason names a state a human chose, and this one names a ticket nobody knows is stuck. It is told once, and the marker at the head of that comment is what keeps the next sweep quiet, the way the reconciler's no-ticket mark does.

## Reconciler

Every sweep (`factory-sweep`, `workflow_dispatch`, not the issue-event runs) also repairs states stuck past their deadline, so a lost event costs at most one sweep (#35). A second sweep over a healthy repo changes nothing.

- A ticket in `agent:implement` or `agent:in-progress` with no live implement run, or a PR in `agent:review` (`agent:implement`, `agent:in-progress`) with no live review run, gets its label removed and re-added with `FACTORY_PAT` so the event fires. A second miss on the same stranding escalates to `needs-human` with a comment, on the retry handler's escalation label set, and a PR's ticket is parked with it.
- A cancelled run is a lost event like any other and counts as a miss: nothing cancels a run for a reason to forgive now that the per-account cap is gone (#149). The marker also carries a re-dispatch count that caps re-dispatches of any cause at two on one stranding, which is what ends a stranding carrying markers the cap wrote as `miss=0`.
- A factory PR still without auto-merge past the stuck deadline has it re-armed, so a refusal on the implement run's non-fatal step cannot leave the PR unmergeable and skipped by update-branch forever. A refused re-arm is a `::warning::` naming the PR and `scripts/onboard.sh`, not a failed sweep, for the same reason that step is non-fatal; `needs-human` or `agent:blocked` is how a maintainer keeps auto-merge off a factory PR.
- A factory PR with auto-merge armed and no `factory/verdict` on its head gets `agent:review`. A PR with a passing verdict sitting behind main with no update-branch run in the window gets a `factory-update-branch` dispatch.
- Any other PR on main with no `factory/verdict` on its head gets `agent:review` at the verdict deadline too, armed or not and whoever opened it (#182). It is the one route onto the judged path nobody opted into, so four reasons leave a PR alone, and its log line says `left alone (<reason>)`: `draft`, since a draft is its author saying not yet; `fork`, which `agent-review.yml` would refuse; `no-ticket`, since with no `Closes #N` the verdict is a mechanical fail, and the one reason the sweep says out loud, once, on the PR itself (#230); and `untrusted-ticket-author`, the trust policy refusing whoever opened that ticket on the `ticket-author` channel, the same question the reviewer asks of it (#179), with an author the sweep could not read counted as refused. This rule asks for the verdict and never arms auto-merge. Once judged, though, the PR carries the verdict section and is a factory PR from the next sweep on, so the bullets above apply to it, and the re-arm at the stuck deadline is one of them (ADR 0007).
- The counts are a `<!-- factory:sweep miss=n tries=m -->` comment on the subject, and one log line per decision names the state, the deadline and the action. A sweep that cannot read the repo aborts with one `::error::` line rather than repairing from a partial snapshot.
