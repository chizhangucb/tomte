# Onboarding

The reasoning behind README's onboarding steps, plus what to re-copy for a target onboarded earlier. None of it changes the steps. The token-scope decision (#20, corrected #252) is the pinned note in `docs/pipeline.md`.

- **`factory_ref` and the ref in `uses:` move together.** GitHub gives a cross-repo reusable workflow an empty `job_workflow_sha`, so the scripts are checked out at `factory_ref` while the workflow file comes from `uses:`. Change one without the other and they drift.
- **What `FACTORY_PAT` cannot do.** It cannot write commit statuses or repo variables, hence statuses on `GITHUB_TOKEN` and the factory's own state on a `factory-state` branch.
- **The label vocabulary `scripts/onboard.sh` creates**: the factory's own (`ready-for-agent`, `hold`, `agent:*`, `needs-human`, `factory:retry-1`), the five triage roles (`needs-triage`, `needs-info`, `ready-for-human`, `wontfix`, and `ready-for-agent` again, which is both), the two triage categories (`bug`, `enhancement`) and the five `wayfinder:*`. #176 added `needs-info`, the categories and the wayfinder set: `setup-matt-pocock-skills` writes the role-to-label mapping and creates no label, so before that they were made by hand per repo or were simply missing, and `gh issue create --label <missing>` fails rather than creating one. `bug`, `enhancement` and `wontfix` are the ones a target almost certainly already has, with GitHub's wording; a re-run rewrites those descriptions to the ones in `docs/agents/triage-labels.md` and the triage skill, which is the point, but it is also the one thing onboarding changes about a label the target already had. The script deletes nothing and never will: it prints the unused GitHub defaults with the `gh label delete` command, for a human to run or ignore, and `note_unused_defaults` in the script is the list. Unused means nothing in the factory or the triage vocabulary reads them; the note is printed unconditionally rather than read off the target, so check each one is actually unused there before pasting. A target onboarded before #169 has no `hold`; re-run the script to get it (`scripts/onboard.sh owner/repo`), remembering that the same run rewrites the ruleset. Since #228 the script reads no commit, check run or commit status at all: a re-run naming nothing keeps exactly the own checks the target's `factory` ruleset already requires, a first run naming none refuses unless `--no-own-checks` says the target has none yet, and a run that would stop requiring one refuses unless `--allow-drop` says to let it go. Every refusal is before the first write. The re-run also re-writes every other label's description. `hold` is an ordinary word: check first whether the target already uses that label for something of its own, because `--force` rewrites it in place and every issue already carrying it becomes a held ticket.
- **Onboarding writes one file to a target, and only to one with no CI** (#242). No workflow of the target's own runs on a pull request: it writes `.github/workflows/check.yml` from `templates/rollup-check.yml`, the roll-up check `check`, with the caller's install command, test command and Node version in it, and requires `check`. One command, no flag; `--no-own-checks` writes no file. A target that has CI is never written to, and a first run naming nothing there refuses with the roll-up to paste, that repo's own job names already in its `needs`.
- **Becoming a target arms every open `ready-for-agent` ticket at once.** Before a repo has a caller, `ready-for-agent` is a note between humans: nothing reads it, so nothing acts on it. The moment a dispatcher starts reading that repo the same label becomes a dispatch order, on every open ticket carrying it, without anyone having relabelled anything. So sweep the backlog before the caller lands: put `hold` on everything that is not actually meant to run, or take `ready-for-agent` off it. That is the new target's own backlog, and it belongs to whoever adds the caller. This repo is the live example: a backlog of open `ready-for-agent` tickets and no caller reading them.

## Migrating a target onboarded earlier

The caller lives in the target and nothing in the factory can see a target's copy, so `templates/factory.yml` drifts silently as it changes here. Re-copy it for a target that predates any of these:

- **#61, the `agent-` prefix.** A caller still naming `implement.yml`, `review.yml`, `implement-pr.yml` or `audit.yml` fails at startup and kills the whole run.
- **`statuses: write`, `checks: read`, `actions: read`.** A called workflow cannot exceed its caller's permissions, so a caller predating these lines needs them added by hand.
- **#171, the pause gate.** A caller with no `vars.FACTORY_PAUSED` gate cannot be paused, and `gh workflow disable factory.yml` is its only breaker. The heartbeat's half of the pause (#256) needs no re-copy, since it reads the variable off the target; on a caller with no gate, setting the variable stops the sweep and nothing else, a half-pause rather than a breaker.
- **#213 then #236, the open-ticket guards.** Before #213 a label or assignee removal on a *closed* ticket wakes a sweep that dispatches nothing, one billed minute each; #236 put the same guard on the two `labeled` clauses across both the `dispatch` and `implement` jobs, so re-copy both.
- **The trigger set.** A caller subscribing to `closed` and `labeled` alone keeps working but waits up to one heartbeat interval instead of dispatching the moment a human removes a blocker. Re-copy the `on:` block and the `dispatch` job's `if:` together.
